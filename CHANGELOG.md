# Changelog

All notable changes to this project will be documented in this file.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- `pi-roundtable-web`: keyboard shortcuts in the owner app. Alt+↑ / Alt+↓ (Option on a Mac) go to the previous or next room in the order the room list shows (folders respected, a folded folder skipped unless it holds the open room, threads after their room, no wrapping), and Alt+Shift+↑ / Alt+Shift+↓ to the previous or next room with unread messages. Switching uses the router as a click does and scrolls the open room's row into view; it works on a page with no list too. In a text field the arrows act only when the field is empty or the caret is at the very start (up) or very end (down) with nothing selected, and nothing acts while an input method composes. Esc closes the topmost menu or sheet and otherwise lets go of the message box without touching its text. `?` outside a text field opens a sheet that lists the keys (a lazy chunk; en and zh-TW wording). Ctrl/⌘ K, which opens the search, now also ignores an input method's composition. The handler is a part that loads after the first paint, about 0.1 KB gzipped more in the first load.

## [0.26.2] - 2026-10-30

### Fixed

- An agent answering in a room of another surface (the web app's `app:agent.<name>`, group and host rooms) no longer believes it is on Discord. The agent addendum and the group seat text now say where this conversation is, from the new optional `ChatSurface.label` (Discord, the web app, the web chat and LINE supply theirs; the key prefix is the fallback), and which other surfaces the agent has places on, and the shared prompts no longer carry Discord's Markdown guidance: how a reply renders comes from each surface's `formatting`, as before. The tool description of an agent's display name no longer says "Discord messages".
- A card answered after its turn stopped waiting no longer leaves a release that any later identical call can spend. The release now expires an hour after the answer, is spent only in a turn whose speaker is the person who approved on the card (or an owner; a surface that does not say who approved leaves it to any speaker), never in a turn without a speaker such as an automatic, scheduled or agent-message turn, which shows the card again, and is dropped when the identical tool call runs without a hold, as that is the run the person approved. Before, it was kept for the life of the gate and spent by whichever turn made the identical call next, so an automatic turn could run a call on a stale approval with no card. A late approval still releases exactly one call, in the turn it starts. See [the plugin guide](docs/plugins.md).
- Agent messages (`message_agent`) and their answers no longer get lost when the host stops: a message sent while the host shuts down, and the follow-up turn that carries a target's answer back to the sender, used to be refused by the stopping queue and only logged, so after the restart the sender waited for an answer that never came. They are now written to the new table `agent_outbox` (additive migration `agent-outbox`, in the agent server's migrations) when the queue refuses them, and the next start delivers them oldest first through the conversation they addressed, once: an entry leaves the table when its turn starts, so a second start or another host reading the same table does not run it again. The normal path writes nothing and is as fast as before; the shutdown waits for the write. An entry whose agent was archived or moved to another channel meanwhile is dropped with a warning. A request's thread is closed when it is refused, so the replayed answer returns to the sender's room.
- A turn nobody is present in (a schedule, an agent's message, an agent's opening task) that ends with an empty final answer no longer fails with "the final assistant message has no text": it ends quietly, posts nothing, wakes nobody (an agent that answers a message with nothing sends no answer back and no follow-up turn), and logs `unattended turn had nothing to say; nothing posted` once. A schedule that says "send nothing if there is no progress" therefore works. A turn someone waits on (an owner's message, a report turn, a remote caller's turn) keeps failing on an empty answer. The new `TurnRequest.unattended` and `ConversationTurnInput.unattended` mark such a turn; the agent server sets them for schedules, agent messages and opening tasks, and `pi-roundtable-webchat` for its background turns that are not reports. A turn that leaves them out is attended, as before. `turnAnswer` takes the new `attended` argument.
- A turn nobody is present in that reaches its time limit still stops at it (it can show no card), but the notice it posts now says that no one was in the conversation to ask for more time and how to allow more (`TurnTimeout.unasked`, en and zh-TW), so the owner can see where an agent's first task or a schedule stopped.
- `ask_user` in a turn nobody is present in refuses at once with a message that tells the model to write the question as its final answer, which is posted to the agent's room, instead of the earlier one-line "ask in your reply".
- `pi-roundtable-web`: `auth.reauthHours` now holds on an open socket, not only on HTTP. The socket's 30-second recheck used to look only at the session's own idle limit (`sessionDays`), so a person removed at the provider who kept a tab open kept receiving room frames, and kept firing `auth.onSessionVerified`, until that limit. Past `reauthHours` the recheck now closes the socket with the code the page already handles for an ended session, so it shows sign-in again, and `onSessionVerified` is reported only for a session inside `reauthHours` on both the socket and HTTP paths. With `reauthHours` unset nothing changes. The check is one extra column comparison in the recheck's existing session query.
- `pi-roundtable-web`: the knight sheet's profile line names an automatic thinking level in words ("Automatic", zh-TW has its own wording) instead of the raw `auto`.
- `message_agent` delivers into the conversation the target agent used most recently, not always its Discord channel. An agent has a conversation on each surface (`discord:<id>`, `app:agent.<name>`), so a reminder to an agent that was working in the web app now lands there, and the agent answers in the web app. The answer and the follow-up turn it wakes return to the conversation the sender wrote from. A message from a room never follows that latest conversation out to Discord, so what was said in an owners-only web room is not posted into the target's Discord channel; it goes on following it from Discord into a room, and `conversation: "discord"` still chooses Discord. The last conversation of each agent is kept in the table `agent_latest_conversation` (additive migration `agent-latest-conversation`), so it survives a restart. An agent that has run no turn yet is reached on the sender's surface, as before.
- `schedule_list`, `schedule_update` and `schedule_cancel` of an agent now cover all its own schedules across its conversations (Discord channel and rooms), not only the current channel's. A schedule made in the web conversation can be listed and edited from Discord, and the list says where each one fires. Another agent's schedules are still read-only by name (`agent`, taken by `schedule_list` alone) and never changed: `schedule_update` and `schedule_cancel` ignore `agent`, which they used to honor undocumented.

### Added

- `pi-roundtable-web`: opening a room from a seat of the round table is a dive: the view zooms toward the seat that was tapped, creeping at first and then rushing in (`cubic-bezier(0.7, 0, 0.84, 0)`, about 380 ms), and the room settles in already at full size, with no blank frame. A mouse click, a tap and a key press on a seat all do it, and the camera of the 3D table dives into a seat from the whole ring the same way. It uses transform and opacity only, a second tap during the zoom is dropped, Back or leaving the table mid-zoom gives the view back and opens nothing, and `prefers-reduced-motion: reduce` switches at once. The code is part of the round table's lazy chunk, not the first load.
- Discord embeds are read as text. A message's embeds (author, title, description, each field as `name: value`, footer, link) are added to the inbound text after its own content, so a post that is only an embed, such as a CI bot's or an alerting tool's webhook post (Discord renders a Slack-compatible webhook's attachments as embeds), now starts the same labelled report turn in an agent's channel as a text post: before, its text was empty and no turn started. The text is plain, markup is left as the sender wrote it, and the embeds add at most 4,000 characters, cut with `…`. A replied-to message's embeds are read the same way, and `discord.channelContext` lists them after a message's text, so an alert in the channel's history is no longer blank. Always on; a message without embeds reads as before. See [the plugin guide](docs/plugins.md).
- `agent_create` takes `long_running`: `true` turns on long-running mode for the new agent's conversations (its Discord channel and its rooms) before its opening task starts, so the first task is not stopped at 10 minutes. Only an owner's turn may; any other tier or the host's own turn is refused before anything is made, and so is a host without the `modes` service. The agent team takes the new `modes` option, which the agent server fills from `MODES`.
- A schedule may carry its own time limit: `time_limit_minutes` on `schedule_create` and `schedule_update` (1 to 240, `MAX_SCHEDULE_TIME_LIMIT_MINUTES`; `null` on update removes it). It replaces the 10-minute default for that schedule's turns and never passes the long-running cap (`autonomy.longRunning.maxSeconds`). Additive column `schedules.time_limit_minutes` (migration `schedules-time-limit`); `Schedule`, `NewSchedule` and `ScheduleChange` gain `timeLimitMinutes`, `BackgroundTurn` gains `timeLimitMs`, and `ConversationTurnInput` and `TurnRequest` gain `timeLimitMs`, which a claim's `background` passes on (the agent server and `pi-roundtable-webchat` do).

### Changed

- `message_agent` takes an optional `conversation` to choose the target's conversation: `"discord"`, `"web"` (or the name of a surface that hosts rooms), or one of the keys `agent_get` lists, which now has a `Conversations:` line marking the most recent. A conversation the target does not have is refused with the ones it has. `AgentOps.message` and `AgentTeam.message` take the same optional fourth argument; `schedulesExtension` takes an optional fifth, the agent's conversations.
- `pi-roundtable-web`: the owners' round table also seats the host rooms the owner may list, so a host whose assistants live in host rooms (for example a support desk's ticket rooms) and has no core agent team no longer shows an empty table. The agents sit first as before, then the host rooms of every kind the owner may list, newest first, by the same lists and `access` as the member and admin table; a room the kind does not list for the owner is no seat. A seat opens the room's own page. The server decides what is seated: the page seats host rooms only where the config names kinds of room for the visitor, so a host with no host room kinds sees exactly what it saw before, and there is no new option.

### Fixed

- `pi-roundtable-web`: the Files page no longer flashes when you switch folders. Every move re-mounted the whole page: the tree collapsed to a "...", the list turned into grey skeletons and the whole screen cross-faded. The page now keeps one name across places and a move inside it skips the view transition. A folder that was listed before shows at once and is fetched again behind it, a folder not seen yet leaves the old rows in place, dimmed after a beat, until its own rows arrive, a branch of the tree opened a second time keeps its rows, and a new folder opens at its top while a refetch of the same one does not move it. The files' stylesheet now loads with the Files page instead of with every visit, which makes the first load about 1 KB gzipped smaller and pays for the drop-down style.
- `pi-roundtable-web`: the drop-downs (the Files page's workspace picker, the model, archive and notes pickers, and the host forms) have one look: the inputs' height, radius, border and focus ring and one chevron of the icon set, in place of the system's inset control. The workspace picker is a pill of the breadcrumb chips' height and tint, and under a coarse pointer a drop-down's text is 16px so iOS Safari does not zoom in when it takes focus.
- `pi-roundtable-web`: the round table's message box had a vertical three-dot button at its end that hid the box and gave no hint of it. It is now a chevron that points where the box goes (down to tuck it away, up to bring it back), with a tooltip, so it no longer reads as a second "more" beside the three horizontal dots.

## [0.26.1] - 2026-10-30

### Added

- `pi-roundtable-web`: typing `@AI` as the first word of the composer works as the toggle in a room that offers it: the switch shows on while it is there, and the page sends an explicit turn with the token cut from the text. Pasted text, a mention later in the text and an address like `a@ai.com` do not count, and the server never reads a message's text for it.
- `pi-roundtable-web`: internal notes in an agent or group room: an agent or group room that more than one person reads (the host has more than one owner) gets an `@AI` switch on the composer, on by default. Off, the message is an internal note: it is stored in the room's log with its author, shown live to every other owner and in the history with the author's name and picture and an "Internal note" marker (zh-TW has its own wording), and never given to the agent: no turn runs, it is not in the agent's session, and it is not in any channel context. The server says which rooms take notes: `RoomView.notes` is `true` on the agent and group rooms of a host with more than one owner, absent otherwise, so the page does not guess. A note is a `send` frame with `mode: "note"` (the frame the host rooms already use); a stored note carries `RoomMessage.note: true` (additive column `web_room_messages.note`, migration `web-room-messages-note`). A host with one owner behaves exactly as before: no switch, no new field in the room list or the history, and a `note` frame is still refused as `bad_frame`. The fixture takes `FIXTURE_OWNERS=2` to try it with Ada and Bob.

### Fixed

- `pi-roundtable-web`: a folder's header no longer turns into an unreadable light fill with white text when the pointer rests on it (on a phone the highlight stuck after a tap), and its title is left-aligned, not centered. The base rule `button:hover:not(:disabled)` out-specified the header's own style; its hover, press and keyboard focus now tint the label and keep its text colour in every look and scheme.
- `pi-roundtable-web`: a row of the room list that is held and dragged on an iPhone now lifts and reorders. iOS Safari lets a page stop a finger's scroll only if a non-passive `touchmove` listener existed when the finger went down; the lift added its own after the hold, so the first move scrolled the page and the browser cancelled the drag. While a row that can be lifted is on the page, a no-op non-passive `touchmove` listener is now held.
- `pi-roundtable-web`: the plain room list (no pin and no folder yet) keeps Agents and Groups by latest activity, as the arranged list and the drawer do. Before, it kept the order the server listed them in, so a room you had just talked to did not move up, even after a reload.

### Added

- `HoldDescription.onDeclined` (hold answers `{ text, onDeclined }`): called once when the call's approval card is declined, also after the turn stopped waiting, so the plugin that held the call can close what it opened for it, such as its own approval notice. Not called for an approval, an expiry, a withdrawal through `supersede` or a message that does not confirm the call; what it throws is ignored. See [Hearing that the card was declined](docs/plugins.md#hearing-that-the-card-was-declined).
- `pi-roundtable-web`: `HostCard.keep`: a card the host still wants (a ticket's pinned card while the ticket is open) survives its kind's `retention.textDays` sweep for as long as `card` or `updateCard` passes `keep: true`; `updateCard` without it makes the card ordinary again. Adds the migration `web-host-cards-keep` (a `keep` column).
- `conversations.keep(record)` (config; `ResolvedConfig.conversations.keep`): asked for each conversation the retention sweep would delete after its kind's `keepDays`; `true` keeps it until the next sweep, so a host can hold a conversation it still wants, such as a support conversation whose ticket is open. A `keep` that throws keeps the conversation and is logged. `ConversationSweep` gains `kept`. See [Conversation retention](docs/plugins.md#conversation-retention-conversationskeepdays).
- `pi-roundtable-web`: `WebApp.rooms.context(room, { limit?, messageChars? })`: a host room's recent messages as the channel-context block `CHANNEL_CONTEXT.read` gives a turn, for a host that starts a turn from a room's `send` hook and has no addressing message. It marks nothing handed over, so a retry reads the same.
- `pi-roundtable-web`: `auth.onSessionVerified(principalId)` for `oidc`: called when a request or an open socket proves a live session, at most once per session every five minutes, so a host can count a person who only has the app open as present. It is not awaited; an error it throws is logged and never fails the request.

### Changed

- `pi-roundtable-web`: an ordinary folder is a light section header (chevron, name, count, ⋯), left-aligned like the Home and Pinned labels, not the boxed grey card, which stays for the archive. A folded folder shows a small overlapping stack of the pictures of its first four rooms and, when it holds more, how many more (`+2`).

## [0.26.0] - 2026-10-30

### Added

- `IdentityService.peek(facts, { conversation }?)`: who these facts resolve to now, read only. It never links, claims, admits, records the person as seen or touches a tier, also when it refuses, and its tier is exactly what `resolve` gives (the lasting roles together with what the access rules give the facts), never the tier last recorded. It answers undefined for an unlinked identity, a disabled principal, or no tier. **Breaking** for code: a hand-built `IdentityService` stand-in adds `peek` (`testHost` and `servicePair` already cover tests).
- `ActorFacts.partial`: a surface that is not the authority on a person's roles marks its facts `partial: true`, and `resolve` records no lower tier and no refusal from them. Optional, not breaking.
- `PROFILES` (`PersonProfiles`), provided by the `identity` plugin: how the core names a person (D1, D3). A plugin registers a `ProfileSource` per provider (`provider`, `label`, `modelVisible`, `pictureHosts`, `fetch(subject, signal)`); a signed-in session reports the name its identity provider gave with `observed(principalId, provider, name)`; the person chooses which linked account represents them with `choose` (refused for an unlinked provider; `null` returns to the default), else the first provider in the new `profiles.prefer` they have linked; `of(principalId)` gives the name, the source and whether a picture exists, and `picture(principalId)` the picture through the source's allowed hosts only (https, no redirect, PNG/JPEG/GIF/WebP, at most 2 MiB, `nosniff`). Fetched and observed names and picture addresses live in memory for an hour at most and are written to no table; a fetch has two seconds and a miss, failure or timeout is remembered for ten minutes. Only the choice is stored, in the new `principal_profile_choices` table (migration `principal-profile-choices`, additive). Types: `ProfileSource`, `PersonProfiles`, `PersonDisplay`, `ProfileRules`, `ProfilesConfig`.
- **Breaking** for a host that replaces the `identity` plugin: it now provides `PROFILES` too, so a replacement lists `PROFILES` in `provides` and `replaces`, as it already does for `IDENTITY_LINKS`.
- `profiles.modelVisible` and `profiles.prefer` in the host's configuration. `Speaker.name` from `IDENTITY.resolve`, `peek` and `speakerFor` becomes the profile name for a provider the host lists in `profiles.modelVisible`; a source's own `modelVisible` flag never widens it. With no source, nothing observed and an empty list, every name is as in 0.25. **Breaking** only for a host that lists a provider: its agents then read that name.
- `pi-roundtable-line`: `lineProfileSource(api)`, a `ProfileSource` for provider `line` over LINE's `/v2/bot/profile/{userId}`, with the picture hosts `profile.line-scdn.net` and `obs.line-scdn.net` and `modelVisible: false`.
- `roundtable principal show` prints the profile source a person chose.
- `pi-roundtable/kit`: `oidcProvider` (`oidcProvider(issuer)`) and `oidcIdentity` (`oidcIdentity(issuer, subject)`), the one writer of `oidc:<base64url issuer>[:<subject>]`. `oidcSpeakerId` of `pi-roundtable-webchat` gives the same strings through it.
- `agentServer: { tools: "chat-only" }` (config), `HostEnv.agentTools` and `ResolvedConfig.agentTools` (`"full"` by default, `AgentTools`): the configuration form and the value plugins read as `context.env.agentTools`. `RoundtableOptions.environment.agentTools` carries it for hosts that build their options by hand. With it no agent or persona turn is offered `bash`, `read`, `edit` or `write`: the agent team's selection leaves them out, the agent's prompt says it has no shell, file tools or workspace, its sessions get no workspace, and `SessionFactory` refuses any selection naming one of them (`toolsFor`, `taskTools`) with a `ConfigError`, so the turn fails closed and is logged, whatever built the selection. `RoundtablePlugin.hostAccess?: true` marks a plugin whose tools reach the host (`pi-roundtable-coding` declares it): a chat-only host does not start with one, nor with a plugin whose `agentSelection` names a shell tool, and `pi-roundtable-webchat` refuses a persona `selection` that does. `roundtable doctor` gains an `agent tools` check that prints the mode. A host without the key behaves as before. See [Chat-only agents](docs/plugins.md#chat-only-agents-no-shell-file-or-workspace-tools).
- `conversations: { keepDays: { <kind>: days } }` (config; `ResolvedConfig.conversations`): a daily sweep deletes the recorded conversations of a kind that were last active longer ago, through `ConversationPort.deleteConversation`, skips a busy one until the next sweep and forgets the record with the new optional `ConversationRegistry.remove(key)`. A kind not listed, and a host without the key, keeps its conversations. Type: `ConversationsConfig`. See [Conversation retention](docs/plugins.md#conversation-retention-conversationskeepdays).
- Events: `EventHandlers.action(event)` and the optional `EventSink.action(event)`: a plugin reports what a person did through its surface (`ActionEvent`: `kind`, `actor`, `principalId`, `channel?`, `ok`, `at`, never content) and every plugin's handler hears it; a handler that throws is logged and never stops the others. The core reports none itself.

- Channel context for any surface. `ChatSurface.channelContext(message, options?)` is the new optional method a surface implements; the new built-in `channel-context` plugin provides `CHANNEL_CONTEXT` (`ChannelContexts`: `read(message, options?)`), which picks the surface by the message's channel key as `THREADS` does and returns what it reads, `undefined` for a surface without the method. `DISCORD.channelContext` is unchanged for callers and is the Discord surface's own answer. `ChannelContextOptions.authors(message)` (`ChannelContextSource` in, `ChannelContextVerdict` `"keep" | "skip" | "end"` or `undefined` out) generalises `foreignWebhook` to any message and surface and wins where it answers; `ChannelContextMessage.external` (and `ChannelContextSource.external`) marks an author outside the people the host serves, never an owner, and the block labels it `role="external"`. `ChannelContextSourceAttachment` is the attachment shape of a fetched message. `formatChannelContext` is now defined with the contract types and re-exported by the Discord entry unchanged.

### Breaking

- `HostEnv.agentTools` is required: code that builds a `HostEnv` by hand sets it (`testHost` and `testPlugin` fill `"full"`).

### Fixed

- A held shell command's sentence on its approval card shows the command's first line, cut at 120 characters, instead of up to 600 characters of every line inside one code span: a multi-line script (a heredoc with `# comments`) broke the card's Markdown into headings. The card's code block still shows the whole command.
- `agent_create` from an agent's turn in a web room started the new agent's opening task in its Discord channel. It now starts on the surface the caller's turn runs on, as the web app's new-agent form already did; a turn on Discord, or on a surface that hosts no rooms, keeps the Discord channel.

## [0.25.0] - 2026-10-29

### Added

- The agent team can be edited by an owner outside an agent turn, with the operations the agent tools use. `AgentTeam` gains `createAgent(speaker, input)` (the fields of `agent_create`, `NewAgent`, plus `model` and `thinking`, checked before a picture or channel is made; without a `task` the agent only exists, and `openIn` names the surface whose room runs the opening task), `archive(caller | undefined, name)` (an owner has no calling agent), `restore(name)` and `remove(name, cleanup?)` for an archived agent or group (`cleanup` is the caller's part of the delete: it runs once the checks have passed and before anything is deleted, and one that throws leaves the target in place to delete again), and `createGroup` and `updateGroup`. Restoring moves a Discord channel back out of Archive (a new channel replaces one deleted meanwhile); an agent does not rejoin the groups it left, and a group needs all its members active. A group that an agent's archive would leave with fewer than two members is archived whole, its members kept, and restores once they are all active again. Removing frees the name, detaches the agent's skills, clears its group cursors and a group's messages, makes the runtime forget the conversations the name kept (an agent's own, its seats in every group, a group's members' seats), and leaves a Discord channel under Archive; an agent the host's seeds name is refused, since the next start would seed it again. Editing a group starts the seats of the members it removes over. `AgentTurnRunner` (the part of the runtime the agent team drives) gains `deleteConversation`, so a hand-built runner for the team must set it. The store gains `restoreAgent`, `restoreGroup`, `checkRestorableGroup`, `deleteAgent` and `deleteGroup`. `AgentTeam` has new required methods, so code that builds an `AgentTeam` by hand (a test stand-in) must set them.
- `pi-roundtable-web`: make, archive and arrange agents from the app. The **+** button of the room list and the drawer opens New agent (name, permanent name, prompt, model, optional opening task and a look from the creator; the new agent's room opens), New group and Archived. The agent sheet gains a Skills section (a switch per skill of the host's catalog; built-in ones stay on) and Archive; a group has a sheet for its name, members and host. Archive asks first and names the agent or group, and Archived lists what was archived with Restore and Delete, which asks first too and frees the name. New owner-only routes carry it: `POST agents`, `POST agents/<name>/archive` and `restore`, `DELETE agents/<name>`, `GET`/`PUT agents/<name>/skills`, `POST groups`, `GET`/`PATCH`/`DELETE groups/<name>`, `POST groups/<name>/archive` and `restore`, and `GET archive`. The new sheets load on demand. The package's changelog has the detail.
- Prompt texts and skills the owner edits outside an agent turn. A new built-in `prompts` plugin provides `PROMPTS` (`PromptDocuments`): named prompt documents, each with a file version, an override stored in PostgreSQL (additive migrations `prompt-overrides` and `prompt-history`) and a history of who changed what and when. `register(spec)` (`PromptDocumentSpec`: `id`, `label`, `description?`, `default` as a string or a function read at each use, `maxChars?`) returns a `PromptHandle` whose `text()` a plugin reads when it builds a prompt; `set(id, text, by, base?)` stores the override, which wins while it is set and applies from the next turn without a restart; `revert(id, by, base?)` returns to the file version; a `base` that is not the text in force when the write takes its turn in the queue refuses it with `PromptConflictError` (carrying the current document), so two saves from one text give one write; a function `default` that throws is an `AgentError` when the document is registered, and later (the file was removed) makes `text(id)` throw naming the document and log an error, ends the run that read it (a persona or an agent's prompt) instead of leaving it with the old text, and marks the document `broken` in `list()` and `get()` (empty `fileText`, `set` and `revert` refused) without failing the others; `list`, `get` and `history` read it (`PromptDocumentView`, `PromptVersion`). The core registers `shared` (`prompts.shared`) and `guest` (`prompts.guest`); a plugin registers its own, such as a persona's prompt. It is on by default because nothing is overridden until the owner saves a text and the file stays the default; at start the host logs one warning per document that differs from its file version, naming who set it and when. A directory agent keeps its stored prompt as the source (seeds do not overwrite an existing row): `AgentTeam.update(name, change, by?)` now records who changed the prompt, and `AgentTeam.promptHistory(name, limit?)` lists the versions. `SkillRegistry` gains `document(name)`, `saveDocument(name, text, baseHash, by)`, `createDocument(text, by)` and `documentHistory(name)` (`SkillDocument`, `SkillVersion`): an agent-written skill's whole SKILL.md with its SHA-256 hash, saved against that hash with the skill tools' frontmatter rules, refused with `SkillConflictError` (carrying the current document) when it changed meanwhile, and kept as versions. `skill_create` and `skill_update` take their turn in the same queue as an owner's save, so neither overwrites the other unseen, and they record the agent's name as the author of a version. `AgentTeam` has the new required `promptHistory`, and `SkillRegistry` four new required methods, so a hand-built stand-in must set them. See [`PROMPTS`](docs/plugins.md#prompts-prompt-texts-the-owner-edits).

### Security

- A seeded generative differential test for the shell hold rule (`shell-policy.fuzz.test.ts`) composes random command lines from the grammar of bash, plants `sudo marker` in them, and runs each in bash 3.2 and 5 on a PATH of stubs: whenever bash runs the stub, the rule must hold the line. A long run (more than 100,000 lines) found gaps that the hand corpus had missed, all now held (the minimized lines are in the hand corpus too): a `NAME+=value` before the command (`A+=b sudo x`); a wrapper option that takes an argument, so that the argument was read as the command (`env -u FOO sudo x`, `exec -a name sudo x`, `timeout -s KILL 5 sudo x`, `nice -n 5`, `stdbuf -o L`, `xargs -I {} sudo x`, `-n`, `-P`, a fractional `timeout` duration), and `env -S`, which splits its argument into a command line and is now held as `shell.unreadable`; a descriptor duplicated or closed for input in front of the command (`<&0 sudo x`, `0<&- sudo x`); a subscript that a builtin evaluates (`declare 'a[$(sudo x)]=1'`, `read`, `printf -v`, `typeset`, `local`, `export`, `unset`), now `shell.unreadable`; `PS4`, `PROMPT_COMMAND` and the other self-running variables assigned on their own (`PS4='$(sudo x)'; set -x`) or after `!`; a backslash before a double quote in a backtick substitution inside double quotes, which bash takes out; a variable the line writes more than once, whose value the rule cannot follow through a loop, `read`, `declare`, `eval`, a function or a branch (`x=ls; for x in sudo; do $x; done`), which is now unknown, so a command name or an `rm` operand built from it is held; and a shell that reads its script where the line does not show it as a word: `echo 'sudo x' | bash`, `bash <<< 'sudo x'`, a here-document, `source <(…)`, `. /dev/stdin`, a file the line wrote earlier (`echo 'sudo x' > f; bash f`, `./f`, `source f`), and anything `xargs` fills in from its input (`xargs bash`, `xargs env`, `xargs -I{} {}`), all held as `shell.unreadable`. Running a script file the line did not write stays unheld, as does any other program. See [the shell rule](docs/plugins.md#the-shell-rule) for how to run the fuzz.
- The web app can run turns, approve held actions and turn yolo mode on, so its authentication guards the owner's power over the agents. `auth: { mode: "none" }` and `{ mode: "password" }` resist the network but not an agent whose shell runs as the service user, which can reach the listener's socket, the password variable and the session key, and so act as the owner. Only a `verifier` (for example Cloudflare Access, whose signed token an agent cannot forge) resists it. The package's README has the threat model.
- Yolo mode approves a held call itself, so it is bounded: only for an owner other than `SYSTEM_PRINCIPAL` (a webhook or a report turn never counts), never for a call that names approvers or is the speaker's alone, never for a class `YOLO_CARDED_SHELL_CLASSES` lists unless `autonomy.yolo.allow` names it, and a call held without classes always asks. **A plain `git push` and a write outside the workspace are approved under yolo.**
- The shell hold rule no longer holds arithmetic. Words inside `$(( ))`, `(( ))` and `for ((;;))` were read as a command, so `echo $(( $n + 1 ))`, `n=$(( $(date +%s) - start ))` and `(( $n > 3 )) && echo big` were held as `shell.unreadable` in every mode; they are dropped once the group closes with `))`, while a `$(…)` or backtick inside still runs and is judged, and `((a); (b))`, `$((a); (b))` and `$( (a) )` are subshells as before. `bash -c 'echo $(date)'` is no longer held: a script is held whole only when the outer shell expands a substitution in it (an unquoted or double-quoted `$(…)`, as in `bash -c "echo $(date)"`); a literal script is judged like any line, so `bash -c 'sudo x'` still holds.
- The shell hold rule closes the gaps the widened differential test found: `trap 'sudo x' EXIT|ERR|DEBUG` is judged as a script; `alias NAME=…`, an assignment to `PROMPT_COMMAND`, `PS0`, `PS1`, `PS2`, `PS4`, `BASH_ENV`, `ENV` or `SHELLOPTS`, and `${x@P}` are held as `shell.unreadable`; a NUL byte is dropped as bash drops it; and a line that evaluates arithmetic (`(( ))`, `$(( ))`, `$[ ]`, `let`, `declare -i`, `[[ a -eq b ]]`) and also holds a `$(` or backtick in single quotes or behind an escape is held, because arithmetic runs a `$(` in the value of a variable (`x='a[$(sudo x)]'; echo $((x))`). The last one also holds `echo '$(date)'; echo $((1 + 2))`, a known cost of failing closed.
- The shell hold rule fails closed. Its lexer is rewritten to read a command line the way bash does, because several forms let a destructive command run unheld in every mode: a quote closed inside a nested substitution (`echo "$(echo "x$(echo ")")" ; rm -rf ~)"`), a comment in a quoted substitution (`echo "$(echo hi # )⏎rm -rf ~)"`), a `case` pattern's `)` (`echo "$(case x in x) rm -rf ~;; esac)"`), `\'` inside `$'…'`, an apostrophe in a here-document body (`cat <<EOF⏎it's⏎EOF⏎rm -rf ~`), `${#x}` and `{#}` read as comments, and a line continuation inside a word. It also judges the command behind a leading keyword (`then sudo ls`, `do rm -rf /x`), a descriptor redirection (`3>&1 sudo ls`), `eval`, `bash -c` with clustered options (`-ec`) and `find -exec`; `$'\\x73udo'` is read as `sudo`, and a command whose name is a brace expansion, a pattern or a variable not known (`{sudo,ls}`, `/usr/bin/su*`, `$cmd`) is held as `shell.unreadable`, as is a brace expansion in an `rm` operand. A line it cannot read to the end (over 200,000 characters, nested deeper than 48 levels, a here-document or `case` it cannot place) is held as the new class `shell.unreadable`, which yolo mode cards like every class but `shell.write` and `shell.push`; so is `eval` or `bash -c` of a script built from a variable or a substitution. The old scan was quadratic and overflowed the stack at about 20,000 nested substitutions; the new one is linear. A hold rule that throws, or a `describe` or `holdClasses` that fails in the shell rule, now holds the call, and the `tool_call` handler blocks the call with the failure as its reason (pi already turned a throwing handler into an error result and did not run the call; the block says why). A differential test runs a corpus of lines with real bash (3.2 and 5, on a PATH of stubs): whenever bash runs `sudo`, the rule holds the line.
- The shell hold rule judges a command or backtick substitution inside double quotes like an unquoted one: `echo "$(rm -rf ~)"`, `x="$(dd if=/dev/zero of=/dev/sda)"` and ``echo "`sudo reboot`"`` were copied as text and ran unheld in every mode. Single quotes still hide their content, and an unterminated substitution is judged to its end. A substitution in the target of a redirect or `tee` also cards under yolo (shell.disk); that is a known cost of failing closed.
- The shell hold rule checks the redirect operators `>|`, `>& file` (a target that is not a descriptor number) and `<>` like `>`, so `echo x >| /dev/sda` is `shell.disk`; `2>&1` is unchanged. `tee` is recognised behind a path or a wrapper (`/usr/bin/tee`, `env tee`), so its substituted target is unknown too.

- `drawCodexImage`, `createCodexImages`, `ImageNotGeneratedError`, `CODEX_IMAGE_MODEL`, `CODEX_IMAGES_PROVIDER`, `CodexImage`, `CodexImageRequest`, `CodexImagesOptions` and `CodexFetch` (`pi-roundtable/kit`): the Codex image client and the `codex-images` plugin built on it, so a project imports one implementation instead of copying one. `drawCodexImage({ token, prompt, references?, model?, signal?, fetch? })` draws one image through ChatGPT's Codex backend and returns `{ data, revisedPrompt? }`, `data` being PNG bytes and `revisedPrompt` the prompt Codex says it drew. It aborts with `signal`, both before the response arrives and while its stream is read, and rejects with the signal's own reason, so a turn's `signal?.throwIfAborted()` still sees its own abort; it stops after five minutes with a `TimeoutError`, refuses a stream over 32 MiB (`Codex image response too large`), and reads only the first image. A call that ran and returned no image, and a completed response with no image at all, both throw `ImageNotGeneratedError`: asking again with the same prompt fails again. `createCodexImages({ fetch?, model?, onMissingLogin? })` is the plugin `codex-images`: it fills `providers.images`, reads the `openai-codex` login through `context.apiKey` for each drawing, and passes the drawing's `options.signal` on, so the turn that asked for an image can abort it. `CODEX_IMAGES_PROVIDER` is `"openai-codex"` and `CODEX_IMAGE_MODEL` is `"gpt-6-sol"`, the model that routes the request. The backend is ChatGPT's own, signed in with the owner's ChatGPT subscription, and OpenAI does not document it for this use: it can stop working without notice, and OpenAI's terms for the subscription apply.
- `jevJudge` and `JevJudgeOptions` (`pi-roundtable/kit`): a `Judge` over Jev's hosted service, built on pi-jev-compaction's client (no new dependency), for the `judge` provider. `jevJudge({ apiKey, model?, baseUrl?, timeoutMs?, fetch? })` sends each question as one request: a yes-or-no question as Jev's own question type, a choice answer checked against the options listed, and a score read by criterion index, every probability a number from 0 to 1. Every failure throws a `JudgeError`. A question has its own limit of `timeoutMs` (default 20,000) that also covers reading the answer. An empty or blank `apiKey` throws a `JudgeError` when the judge is made, because the client would otherwise use the key in the environment.

### Changed

- The `codex-images` template (`roundtable add plugin codex-images`) is now a short file that imports its client and plugin from `pi-roundtable/kit` (`createCodexImages`, built on `drawCodexImage`) and makes the `codexImages` plugin your config lists, under the same warning head and still exporting `createCodexImages`, `ImageNotGeneratedError`, `CodexFetch` and `CodexImagesOptions`. Its `images` provider now aborts with the turn that asked (it ignored the `signal` the core's `generate_image` tool hands to a drawer), and it refuses a response stream over 32 MiB; a PNG of about 12 MiB, which the completed event may repeat, can be refused. Its copied test gains one that aborts a drawing through `options.signal`. A plugin already copied is unchanged until it is copied again.

## [0.18.0] - 2026-10-17

### Added

- `OpsAlerts`, `OpsAlertsOptions`, `OpsRaiseOptions` and `OpsAlertKind` (`pi-roundtable/kit`): short alerts for the people who run a host, for a plugin's own faults. `new OpsAlerts({ sink?, logger, kinds?, windowMs?, kindCap?, now? })` posts through `sink(text)`, a function that resolves `true` when it posted and `false` when it chose not to, so the kit names no discord.js type. `raise(key, text, { code?, info? })` posts at once, never queued, a key at most once per window (one hour) and a kind (the key's word before the first colon) at most `kindCap` times per window (8), whatever the keys; what is held back is only counted. A sink that throws or answers `false` gives the key and the slot back, so the next raise tries again; a throw is logged by the error's name and `raise` never throws. `info: true` is news, posted once per key, outside the cap and outside `faults()`. `faults()` lists the last fault of each kind, newest first, with `name` (from `kinds`), `code`, `raised` and `suppressed`, in memory. With no `sink` the alerts are recorded, the key stays held, and the log has one line per window (`an ops alert was raised and there is no sink to post it to`). No summary of the held-back alerts is posted, so there is no new text to translate.

A call never pings anyone it does not name, and a failure is a `DiscordPosterError` whose message holds no URL, webhook token or bot token. Making it sends nothing, so `Roundtable.check()` still never reaches Discord. The interface is `DiscordPoster`; its types are `WebhookPost`, `PosterFile`, `PostedMessage`, `DiscordMessage`, `RecentMessage`, `DiscordCard`, `CardButton`, `CardLink`, `CardSelect`, `ThreadState`, `ThreadCloser` and `CategoryChannel`; its failures are `DiscordPosterError` with `DiscordFailure` and `DiscordReason`; and `DISCORD_LIMITS` is the frozen table of the limits it checks. - `fakeDiscordPoster`, `FakeDiscordPoster`, `FakePosterChannel` and `FakePosterMessage` (`pi-roundtable/testing`): `fakeDiscordPoster({ idOffset?, now? })` is a `DiscordPoster` in memory with its state open to the test. - `fakeDiscord({ poster })` and `testHost({ discord: { poster, channelInfo } })` (`pi-roundtable/testing`) take the poster and the channel lookup the test wants; by default `DISCORD.poster` is a new `fakeDiscordPoster()`, and `fakeDiscord()` exposes it as `poster`.

### Added

- `Roundtable.check()` and `RegistrationReport` (`pi-roundtable`): sets up every plugin as `run()` would and refuses what `run()` refuses (a plugin that adds nothing, a clash, a missing service, a removed field, a bad route), with the same messages, without migrating the database, starting a service, opening a listener or reaching Discord. ## [0.15.0] - 2026-10-14

### Added

- `approvalCard(call, workspace?, limits?, parameters?)` (`pi-roundtable/kit`) takes the tool's parameter JSON Schema, and the confirmation gate passes the schema of the held tool, read from the session's tool list. With it the approval card shows the call as a field list instead of one JSON block: a line `**label**: value` per argument, in the order the schema declares its properties, labelled by the property's `title` or its name, absent arguments left out. An argument the schema does not list follows the listed ones with its name in code format, so it cannot pass for a declared label. Only an argument's own properties count: one named `toString` or `constructor` is shown with its value. A multi-line or long string (a lone `\r`, `\u2028`, `\u2029` and `\u0085` are line breaks too) and any nested value (as compact JSON) go in a fenced block that keeps their line breaks. A value on a line has its markdown, links and `@everyone`/`@here` escaped, as the model writes it; an array of scalars is joined with commas unless an item is empty, shows nothing, or holds a comma and a space or a line break, and then it is JSON; a string that is empty or shows nothing is written out (`""`, `"\u200b"`) so the person sees it is there. The `limits` apply as they did to the JSON: a long string is cut and marked `… [N chars]`, and fields that no longer fit are dropped and listed by label. A tool with no schema, or one that lists no properties, keeps the JSON block, as does a card built without `parameters` (the coding desk's).
- A plugin can withdraw an approval card it caused. A hold answers `{ text, supersede: signal }` (`HoldDescription.supersede`; a tool's `hold` and a rule's `describeInTurn`), and aborting the signal closes the call's approval card, also after the turn stopped waiting and the card stayed open (the Discord message is edited: controls off, the abort reason as footer when it is a text, else "Withdrawn; nothing will run"; the web chat closes the prompt as `withdrawn` with the reason as `note`), forgets the held call so no later approval runs it (a card's late approval, a confirming message, and the saved held actions included), and tells a turn still waiting that the call was withdrawn (`refused: "withdrawn"` in `HoldRefusal`). Whichever of an approval and the abort comes first decides: an approval answered first runs the call once and the abort changes nothing, and an abort first wins whatever a surface then reports, a call it withdrew is never held again; aborting twice does nothing. Withdrawing removes every identical call (same tool, same canonical input) held for the conversation, whichever hold held it. Nothing stays listening once the call is released, refused, dropped, or its card failed. A signal does not survive a restart, so a withdrawal cannot reach a call held before one; a hold that answers an already aborted `supersede` when the call is repeated refuses it without a card and drops a confirmation of it. New in `pi-roundtable`: `ApprovalOptions.supersede` for surfaces (a surface closes the card when it aborts; a card that arrives with it aborted is not shown) and `withdrawalNote` (`withdrawalNote(signal, fallback)`), the footer from the reason.
- `ToolTurn.approvedPrompt` (also `SessionContext.approvedPrompt(toolCallId)`): the id of the approval card that released the call a tool's `run` is making, for a tool that must show a client which approval it acts on. It is set when the person approved the held call on its card, in the turn that asked or, for a card answered after that turn stopped waiting, in the later turn whose call that approval releases; it is undefined for a call that was not held, one a message confirmed (also after a restart, which keeps no cards), one a surface released without a card id, and in a host with no turn. A surface reports it through `ApprovalOptions.approvedPrompt(prompt)` (called before `confirm` resolves `approved`; Discord reports the card id, the web chat the `prompt` frame's id) and `LateAnswer.prompt`; a surface whose cards have no stable id leaves both out.
- `ClientCallOptions.approval?: { prompt: string }`: a tool names the approval a client call acts on, normally `{ prompt: turn.approvedPrompt }`, and the transport hands it to the client beside the call. The web chat writes it into the `client_call` frame as `approval: { prompt }` (a text of 1 to 128 characters, else the call fails); a call without it carries no field.

### Changed

- **Breaking for code that matches exhaustively:** `HoldRefusal` (a tool's end in `TurnProgress`) gains `"withdrawn"`, and the web chat's `PromptOutcome` gains `"withdrawn"` (with `prompt_closed.note`). A switch over either needs a case for it; a web chat client closes a withdrawn prompt as it does a cancelled one.
- **Breaking for third-party surfaces:** `describeSurfaceContract` adds a check that an approval its plugin withdraws (`ApprovalOptions.supersede`) resolves `cancelled` and closes, that one answered first stays answered, and that one withdrawn before it opens is not shown. A surface with approval cards that does not implement `supersede` fails it; the gate still refuses a withdrawn call whatever such a surface reports.
- The web chat's approval prompt `message`, and the text of the Discord card, show a held call as fields rather than a JSON block when the tool's parameter schema is known (see Added). `approval.input` and `ApprovalDetails` are unchanged.
- `@babel/parser` and `@babel/types` move to Babel 8 (8.0.7 and 8.0.6), which read a schedule's precheck script and the files the boundary check scans. Import attributes (`with { type: "json" }`) are on by default there, and `importAttributes` is no longer a plugin name. Babel 8 packages need Node 22.18 or newer, or Bun.

## [0.13.0] - 2026-10-13

### Added

- `formatChannelContext` (`formatChannelContext(messages)`) is exported from `pi-roundtable/discord`, the function that writes `ChannelContext.text` (the `<channel-context>` block with each author in attributes and every `<` neutralised), so a host can test what the model sees without a deep import. It is the function the reader already used; nothing about the block changes.
- `squarePng`, `SquarePngOptions` and `SQUARE_PNG_MAX_SIDE` (4096) are exported from `pi-roundtable/kit`. `squarePng(bytes, { size?, maxBytes?, maxSide? })` is the centered square crop, scaled down to at most `size` pixels per side (default 512) as PNG, that the agent avatars are made with. The header is read before decoding: a declared width or height over 4096 (or `maxSide`) rejects with `ImagePreparationError` (`pixel-limit`, with a message that names the side limit), bytes of no PNG, JPEG or GIF with `invalid-image`; a WebP is refused the same way, since the canvas cannot decode it, and so is any picture that fails to decode. With `maxBytes` the side steps down by a quarter until the PNG fits, and a picture that does not fit at 16 pixels throws a `RangeError`.
- `discord.attachmentDownload: { deadlineMs?, idleMs? }` (each a whole number of milliseconds from 1,000 to 600,000) sets the limits of the downloads of the files of an owner or agent channel message on the agent server: `deadlineMs` is the overall deadline for the message and its reference together (default 60,000) and `idleMs` the time one file may send no byte before it is given up (default 10,000). `attachmentsOf` takes the same two as `limits.deadlineMs` and `limits.idleMs`, and `AgentServerOptions.attachmentDownload` passes them on for a host built without `defineRoundtable`. A file that goes quiet is recorded as `download failed: idle_timeout` and the next file is tried at once.

### Changed

- The avatar studio refuses a drawn picture that declares a side over 4096 (`ImagePreparationError`, `pixel-limit`), where it used to decode it. The configured `avatar` is not held to that: a photo of any side within the 64 MP decoded-pixel budget is accepted, and one that cannot be read as a picture is logged (`the configured avatar could not be used`, with its error code) and replaced by the plain bot, where it would stop the host from starting.
- The default overall deadline for downloading the files of a message and its reference rises from 20 to 60 seconds, since a stalled download is now caught by the 10 second idle timeout instead of by the deadline: a body that sends no byte for 10 seconds (the wait for the headers counts, also for a fetch that ignores its abort signal) ends that file alone, where it used to hold every file still to come until the deadline. A slow download that keeps sending bytes now has up to 60 seconds. A host that wants the old bound sets `discord.attachmentDownload.deadlineMs: 20000`.

The kit exports `InterimPoster` and `InterimPosterOptions`, so a worker of a plugin's own posts its interim text as the host's turns do.

- `PromptWait` and `LateAnswer`: `Prompts.confirm` and `Prompts.ask` take an optional last `wait`, whose `late(answer)` returns the text of a turn for an answer given after the turn stopped waiting. With it a prompt may resolve the new `Approval` `pending`, or `"pending"` from `ask`, and stay open. Prompts without it, such as a coding worker's, wait for their answer or their turn's stop.
- `discord.cardGraceSeconds` (default 120): how long a turn waits on its owner card before it goes on without the answer.
- `HostEnv.scratchDir`: the host's scratch dir, when it has one, so a plugin that runs a shell of its own gives it the same TMPDIR and hold roots as the agents' (`HostEnvironment.scratchDir`; `defineRoundtable` sets it from `scratchDir`).

### Changed

- The agents' prompt tells them to show a file with `attach_file` or a `discord_send_message` file `path`, and never to read an image or base64 a file to send it.
- Owner cards no longer expire after 30 minutes, and say nothing of a countdown. A turn waits on its approval or `ask_user` card for the grace period; answered within it, the turn goes on as before. After it, `ask_user` returns that the person has not answered yet and the model ends its turn saying it is waiting, and a held action is blocked as awaiting approval (not held for a text confirmation). The card stays open for the life of the process, and answering it later starts a turn in the same conversation, as a message from whoever answered: a question's turn carries the question and the answer; an approval lets exactly the call shown on the card run once, under the same gate and tier rules, in the turn that tells the model to make it and report the result; a refusal's turn says so. A late card is edited and disabled as before, and a second press does nothing. A stopped turn cancels only a card it still waits on. A coding worker's cards keep the worker waiting, with no deadline. After a restart a card's press says it is no longer valid and to ask again. The `ask_user` description says so instead of "30 minutes".

### Fixed

- An approval card in an owner conversation sizes a file sent by a relative path from the session's own directory, as the send reads it, instead of showing it as not found.
- The webchat OIDC test of expired and not-yet-valid tokens no longer fails when the clock crosses a second between signing and verifying.

## [0.9.3] - 2026-10-10

### Fixed

- A long non-ASCII upload name no longer fails with `ENAMETOOLONG` on Linux: a stored file name is cut by UTF-8 bytes (150 at most, on a code point, keeping the end so the extension stays) instead of by UTF-16 units, so the file name and its `.json` record fit the 255 bytes a file system takes. A leading dot left by the cut is replaced too. The Discord download path shares the fix. `AttachmentPort.save` removes the data file when the record write fails, so a half-saved file no longer counts as waiting.
- Calls on one principal's attachments run one after another, so two messages that name overlapping files no longer leave the refused one's other files moved into the conversation: `turnAttachments` moves the whole set or none, rolls back a partial move, and answers a file a sweep or a message took meanwhile with `AttachmentRefusal` (`unknown_file`) instead of a raw `ENOENT`.
- The `## Attachments` block prints a name and a content type a prompt can trust: control characters, line and paragraph separators and bidi controls in a name become underscores and quotes become apostrophes, and a content type that is not a plain `type/subtype` prints as `application/octet-stream`.

- `discardPending` removes the staging directories it emptied, so a conversation's uploads leave no empty directories behind.
- `deleteConversation` of the Pi runtime removes the conversation's attachment directory, the files saved for it that no turn used, and its share of the used-bytes tally, so a deleted conversation keeps no files (a conversation deleted in the instant a message is taking its files can leave that message's share of the tally behind).

- `TurnAttachmentOptions` and `AttachmentPort.turnAttachments(channel, principalId, files, options?)`: `options.usedBytesLimit` caps the bytes one principal's turns keep across all their conversations. The core tallies the bytes per principal and conversation, and deleting a conversation gives its bytes back.

### Documented

- The guide says what the port checks (a private conversation's record) and what it does not: a channel with no record, or any channel on a host with no conversation registry, is admitted for every principal, so the plugin that owns a channel checks that the caller may use it before every call.

## [0.9.1] - 2026-10-10

### Fixed

- A SIGTERM no longer lets the host keep taking work until it was idle: in 0.9.0 the shutdown drain only waited, so messages, error and webhook reports, schedules, and plugin turns that arrived meanwhile were served and waited for too, and a host that kept getting them never became idle until the one-hour limit (a deploy waited for systemd to kill it). The drain now starts by closing the channel queue: no new turn starts from any source. A message that arrives is not run and its channel gets one short restarting notice (not for a bot's or an integration's message, which is only logged), including a message that waited behind a running turn, and a message is no longer steered into a running turn; a background turn (a schedule's, a delegated task's report, an error report) is skipped; `context.turns.run`, a task for `context.queue.run` that has not started, and a group's next member's turn are refused (`HostStoppingError`, new in `pi-roundtable`), and so are new worker tasks; a remote MCP run fails instead of starting. The scheduler claims nothing during the drain, so a due schedule stays due and fires after the next start if it is less than twelve hours late. Turns already running finish.
- The drain is bounded by three minutes by default instead of an hour: `drainSeconds` in the config, or `drain.limitMs` in `RoundtableOptions`. At the limit the host stops each running turn as the owner's stop does, gives it `drain.abortGraceMs` (ten seconds by default) to end, hands what is left to `aborted`, and goes on to stop the services and exit. Give the service manager a stop timeout a minute longer than the drain, such as systemd's `TimeoutStopSec=5min`.
- A turn or worker task whose model ignores the abort (a claude-bridge subprocess that stays alive after "turn timed out; aborting") no longer holds its channel, and the drain, for ever: a run still going `turnAbortGraceMs` (15 seconds by default, `PiAgentRuntimeOptions`) after its abort has its session disposed of and ends as failed, and the conversation's next turn opens a new session from its files. An owner's stop of such a turn is guarded the same way.

### Added

- `QueuePort.closed` (`context.queue.closed`): whether the host is shutting down, for a plugin that starts work from its own timer or route.
- The `drainSeconds` configuration key.

Principal and identity attribution replace implicit owner authority.
Ordinary single-owner Discord configurations remain accepted, but direct runtime callers, custom background turns, and web integrations must follow [Migrating to 0.9](docs/migration-0.9.md).

### Added

A corrupt reader record (or an empty reader) refuses every later bridge turn of its conversation, fail closed; start a new conversation to recover (documented in the migration guide). `bridgeHistoryHidesMemory(branch, reader)` takes two parameters: the primary-owner attribution of SYSTEM and of pre-scope memory stays inside the core, and `carriesMemory` names a public message type. In opt-in Pi sandbox mode, `memory.visibility` defaults to `"private"`; set `"shared"` explicitly for a party-wide prompt block, including on a 0.8 upgrade, so it does not taint each participant's reader record.

#### Identity and access

- The built-in `identity` plugin, registered first in every host: the tables `principals`, `principal_identities`, and `principal_roles` (ledger ids `identity/principals`, `identity/principals-claimable`, and `identity/principals-plugin-links`), and a backfill that runs at every boot (`identity/backfill`) and makes a principal of the same id for the configured owner and every person id stored in `owner_memory`, `schedules`, `conversations`, and `held_actions` (a held action that names its `principal_id` for the hold it holds is skipped: its `speaker_id` is an actor id; so is any id a linked identity is known by, its subject or `<provider>:<subject>`, since this version wrote that row). A principal it makes may be claimed once by the person of that id, unless it is a configured owner's, which is never claimable, even after the configuration names another owner. 0.8's `remote-mcp` speaker, the owner writing through an outside agent over MCP, gets no principal of its own: it is linked as `legacy:remote-mcp` to the primary owner's principal, so the schedules it created stay the owner's, at the owner tier. A carried-over author of schedules who is not a configured owner is recorded as seen at the upgrade, at the highest tier they scheduled at but at most the highest tier the access rules could give them (never owner), so their schedules keep running for `backgroundStaleDays` until they are seen again. It only inserts, so no existing row changes, and it logs one line with what it made. A test that lists the host's plugins or migrations now finds `identity` and its four migrations first.
- `IDENTITY`, the identity service the `identity` plugin provides: `resolve(facts, { conversation }?)` turns what a surface reports about a person (`ActorFacts`: `provider`, `subject`, `name`, `roles` written `<surface>:role:<name>`, optional `surface`, `space`, and `legacyId`, the 0.8 speaker id) into a `Speaker` with its `principalId`, or undefined when the access rules serve no one by them. A linked identity is its principal's; an unlinked one first claims the principal of its 0.8 id, so a person carried over from 0.8 keeps their memory, schedules, and conversations; a principal the backfill could only name by its id takes the name the facts carry as it is claimed, while one it named, such as from a schedule, keeps that name. A principal is claimed at most once: only one the backfill made, before any identity is linked to it, and never one holding the owner role, so an identity unlinked by the CLI or dropped from the configuration does not claim it back; otherwise someone the rules admit gets a new `p_<ulid>` principal. A disabled principal is no one; the owner tier comes only from the configured owners or a role the CLI grants, never from a role a surface reports. The tier is the higher of the principal's lasting roles and what the rules give the facts on this contact. Someone refused is not claimed or admitted; a linked person refused is recorded as seen at no tier, except by facts that lack the roles the rules decide by, such as a Discord DM, which neither refuse nor lower anyone on record. The service is read-only to plugins, and what it returns is a frozen copy: `principal(id)`, `list()`, `identities(principalId)`, `roles(principalId)`, `tierOf(principalId)` (the tier of the lasting roles), `owners()`, and `speakerFor(principalId, tier?)`, for a turn started on someone's behalf at their tier or lower (the tier last seen for someone whose tier comes only from the rules, refused after `backgroundStaleDays` or once a contact of theirs is refused), complete it. Principals, links, and roles are written only by the configuration and the `roundtable principal` CLI, and `speakerFor` refuses `SYSTEM_PRINCIPAL`, whose turns only the core starts. Reads are reused for 30 seconds, so a change another process makes is seen within that time. At every boot the configured owners are made, linked, and granted the owner role; an owner or an identity the configuration no longer names loses what the configuration gave it, and a configured owner's identity linked to someone else stops the boot with a `ConfigError`. Types: `IdentityService`, `ActorFacts`, `AccessRules`, `AccessOwner`, `AccessTier`, `Principal`, `IdentityLink`, `IdentityRef`, `LinkSource`, `RoleGrant`, `RoleSource`; values: `IDENTITY`, `SYSTEM_PRINCIPAL`, `IdentityError`.
- The `access` configuration key: `access: { owners: [{ name, pronouns?, principal?, identities? }], admins?, members?, provisioning?, backgroundStaleDays? }`. Identities are written `<provider>:<subject>` (`discord:<user id>`, `token:remote-mcp`, and for OpenID Connect `oidc:<issuer>:<subject>`, the web chat's 0.8 speaker id); roles `<surface>:role:<name>`, such as `discord:role:<role id>` or `web:role:App.User`; `everyone` is `true` for every surface or a list of surfaces. The first owner is the primary owner and needs a `principal` in 0.9, such as the old `owner.id`; with Discord configured they also need a `discord:` identity, which the Discord parts act for. `provisioning` is `"admitted"` (default) or `"linked"`, which serves only identities already linked (by the CLI or as a configured owner's) and claims no 0.8 principal; `backgroundStaleDays` defaults to 30. `access` with `owner` or `speakers`, or neither, is a configuration error. `roundtable init` writes `access` in both templates. Types: `AccessConfig`, `AccessOwnerConfig`, `AccessTierConfig`.
#### Operator commands

- `roundtable upgrade [--write]` rewrites `roundtable.config.ts` in the 0.9 form: `owner` and `speakers` as the `access` they mean (the owner's `principal` is the old `owner.id`, their identity `discord:<id>` on a host with Discord and none without; users `discord:<id>`, roles `discord:role:<id>`, `everyone` as `["discord"]`), and the top-level `discord` as `adapters: [discord({ ... })]` with its import. It shows a diff and writes only with `--write`, after loading the rewrite beside the file and checking that the host would serve the same owners, admins, and members with the same Discord settings. The check loads the file as the host does, so it needs the environment the host runs with: when the file does not load as it is, such as with secrets kept outside `.env`, the preview says it was not checked and `--write` refuses (exit 1) until that environment is set; `--write --unchecked` writes it anyway, with a warning. It keeps every comment and says which it moved, changes no other file, and refuses, naming the line, what it cannot read with confidence, such as an owner built elsewhere or a spread configuration. A second run finds nothing to change.
- `roundtable principal list | show | create | link | unlink | grant | revoke | disable | enable` lists and changes the principals, their identities, and their roles in the host's database. `list` prints each identity as `access` and `link` take it, `<provider>:<subject>`, and says of a principal with none whether its 0.8 id still links its own at first contact; `link` says when it uses up that claim, which no later `unlink` gives back; the owner role is granted only here and in the configuration; `grant` of a role the configuration already gives changes nothing and says so, and `revoke` refuses it, so it stays the configuration's to take away; `unlink` refuses an identity the configuration lists under that owner, whoever linked it (the configuration, a first contact, the CLI, or a 0.8 claim), and also when the configuration's schema rejects it, since a running host would admit it as someone new and the next start would fail on it, and says to remove it from `access.owners[*].identities` instead; it takes one the configuration moved to another owner, as a start that stops on it asks, and says to restart the host with that configuration, unlinking again any new `p_…` principal that takes the identity meanwhile. The owners are read by the configuration's schema alone, so a plugin or model runtime that fails does not pass for a configuration that does not load. A `<principal>` that is both a principal's id and an identity linked to another principal, as a 0.8 web user's id can be, is refused as ambiguous, naming both. A running host sees a change within 30 seconds, which every change says.
- `roundtable doctor` checks `access` (a warning when `everyone: true` admits everyone on every surface of a host with more than one) and the principals: the backfill the next start makes, as a dry run printed as the start logs it, a configured owner's identity linked to another principal, which stops the start, and a disabled owner. A warning, printed with `!`, does not fail the doctor.
#### Plugin and conversation contracts

- `RoundtablePlugin.identities`: identities a plugin's own credentials stand for, each a `PluginIdentity` (`{ identity, principal? }`, the identity written `token:<subject>`, by default the primary owner's; only the `token` provider is accepted, since a surface's identity such as `discord:` or `oidc:` is a person's own account, linked by `access.owners` or the CLI). At every start the `identity` plugin links each one to its principal under the new link source `plugin` (ledger id `identity/principals-plugin-links`), moves one bound to another principal than at the last start, and unlinks one no plugin declares any more; an identity that does not parse or is not a `token:` identity, one two plugins declare, the system principal, a principal that does not exist, or an identity linked to someone else by the configuration, the CLI, or a first contact stops the start with a `ConfigError` that names what to change. A declared identity is never admitted or claimed at a first contact, and its link does not use up the principal's 0.8 claim, since a plugin's credential is not the person's own identity. For the same reason its link never tells which principal a configured owner is: an owner in `access.owners` that lists a declared identity is known by its `principal` or its other identities, and when that is not the principal the plugin binds the identity to on that start (its `principal`, or else the primary owner), or nothing else tells who the owner is, the start stops with a `ConfigError` saying to remove the identity from that owner or bind the plugin to them; `roundtable doctor` reports the same. - `Speaker.principalId`, the principal the speaker is, equal to `id` for a person carried over from 0.8. It is required: a plugin that builds a `Speaker` itself gives it, from `IDENTITY.speakerFor` when it starts a turn for someone. `OWNER_SPEAKER` from `pi-roundtable/testing` has it, and the speakers of `speakerPolicy(map)` have their own id as their principal.
- `InboundMessage.actor`: who wrote the message, as the surface reports them (`ActorFacts`); the Discord surface fills it, with the author's roles as `discord:role:<id>` in a server and none known in a DM, and the web chat with an OpenID user as subject under the provider `oidc:<base64url issuer>`, their roles as `<surface>:role:<name>`, and their 0.8 speaker id as `legacyId`, so a web user the access rules serve claims their 0.8 principal under that provider. A surface that leaves it out has it read from `authorId`, `authorName`, and `authorRoleIds` with its prefix as the provider, with a `deprecated` warning once per surface; that goes away in 1.0.
- `InboundMessage.speaker`: who the author is to the host, set by the router alone before any claim admits the message, through `IDENTITY`: undefined when the access rules serve no one by them, when they cannot be resolved (logged), and for bots and integrations, which are not resolved; a surface's own value is dropped. The author is recorded, such as linking them at their first contact or recording them as seen, only once a claim admits the message, so messages no claim takes link or make no one (an already linked author the access rules refuse is still recorded as seen at no tier as the message is resolved, at most once every few minutes), and what a claim admitted runs even when that record fails; a channel's messages still reach their claim in the order they came. `testPlugin` resolves authors through a given `IDENTITY`, and otherwise only the `owner` is anyone, at the owner tier.

A turn's registration still never changes what the first one recorded. A stand-in `ConversationRegistry` needs the method too.
- `Prompts`, `PromptScope`, and `promptScope`: a running turn's prompts are answered by those its scope names, made with `promptScope(speaker, visibility)`: `principalId`, `speakerId`, `tier`, and `escalate`, `owners` in a shared conversation and `none` in a private one. The speaker answers their own question and approves a call at its `minTier`; where the scope escalates to the owners every owner may answer too, and a call above the speaker's tier is theirs alone; where it escalates to no one, such a call resolves `expired` at once, shown to no one. `ChatSurface.prompts(channel, scope?)` receives the scope; `SurfacePort.prompts` and `RuntimeDeps.prompts` take it, and still take 0.8's `Speaker`, read as the speaker of a shared conversation, with a deprecation warning once per host until 1.0. `OwnerPrompts` is a deprecated alias of `Prompts` until 1.0.

The Pi runtime scopes an interactive turn's prompts by it.

#### Channel context

- Channel context: a turn for a message in an agent's channel also reads the channel messages posted since the assistant's last post there, including those that did not address it, appended to the turn's text after the message (and after the replied-to and forwarded messages) as a delimited block that says they were not addressed to the assistant, each message with its author as separate `from`, `id` and `role` attributes (names lose `"'=<>(),`, and every `<`, also the full-width `＜`, in a message's text becomes `‹`, so a message cannot close the block or forge another), so it lives in the conversation's history, not in the system prompt. It reads Discord as the turn starts: the `fetch` messages before the addressed one (default 50, at most 100), only those after the assistant's latest post there (its bot user's or one of its application's webhooks'), without the assistant's own posts, the addressed message, empty messages, and every message it handed over or that addressed the assistant before in that channel (remembered in memory per channel); other bots are kept and marked, the host's owners marked; consecutive messages of one author at least `similarity` alike (default 0.8) count as one, the later kept; the newest `keep` (default 15) are kept, oldest first; mentions read as names, stickers and files as text with their names and links, never downloaded; a message is cut at `messageChars` (default 500), another bot's at `botMessageChars` (default 80), and near repeats are judged by at most a message's first 500 characters; an option given as `undefined` counts as not given. A Discord error is logged and the turn runs without it. Group rounds read none, since they carry what was said since their last turn, and direct messages never do. It is public channel text: not private memory, never tagged `privateTo`, and the turn's reader stays the person who addressed the assistant; people with no tier are included as channel text but do not become speakers.
- The configuration key `discord.channelContext`: `false` turns channel context off for the host, the agent server and every claim; otherwise `{ fetch?, keep?, similarity?, messageChars?, botMessageChars? }`, the host's defaults, which a call's options override. Prompt snapshot (h) records an agent turn with channel context; (a) through (g) are unchanged.
- A divider after a restart: when a conversation is started over (`conversations.startFresh`, whichever claim owns the channel) in a Discord server channel or thread, the core posts one short public message there as the bot, after the claim's `startFresh` succeeded, so channel context's window, which ends at the assistant's last public post, no longer reads what was said before the restart. The owner's ephemeral reply is unchanged; direct messages and other surfaces get none, and a failed post is logged as a warning while the restart still counts. The configuration key `discord.freshMarker` sets the text (default `─── new conversation ───`) or, as `false`, posts none; a surface contributed by a plugin may implement the optional `ChatSurface.markFresh(channel)`.
- `DISCORD.channelContext(message, options?)`, for a plugin's claim to opt in: call it once per answered message inside the turn's `run`, and append what it returns with `withChannelContext(text, context)`. It resolves undefined in a direct message, on another surface, when the host turned it off, when nothing new was said, and when Discord cannot be read, and never rejects for those; an invalid option (`fetch`, `keep`, `messageChars` and `botMessageChars` not positive integers, `similarity` outside 0 to 1) rejects, a programming error. Types `ChannelContext` (`{ messages, text }`), `ChannelContextMessage`, and `ChannelContextOptions`, and values `CHANNEL_CONTEXT_DEFAULTS` and `withChannelContext`, from `pi-roundtable/discord`. A stand-in `DISCORD` service needs the member; `fakeDiscord({ channelContext })` answers it, by default with no context.

#### Personal background work and delivery

- `PERSONAL_TARGET`, the host's own background target: every person's conversations whose claim answers background turns. The core's `modules` plugin contributes it on every host, with or without Discord, where 0.8's agent server contributed it, so a plugin's conversations on a host without Discord schedule and delegate too once its claim answers background turns. Its name stays `"owner"`, as 0.8 stored it, and its limits are 0.8's. `OWNER_TARGET` is the same target, deprecated until 1.0; a plugin that contributes a target named `"owner"` itself now clashes with it.
- Per-person limits: `BackgroundTarget.schedules.perPrincipal` holds each person to that many of a target's schedules across all their conversations (0.8's `remote-mcp` schedules count as the primary owner's), and `BackgroundTarget.delegation.maxRunningPerPrincipal` to that many delegated tasks running at once. - `RUNTIME`, the runtime every conversation turn runs on, provided by the new built-in `runtime` plugin that every host registers just before the agent server. It is the `runtime` slot's runtime when a plugin fills the slot, and Pi's otherwise; `AGENTS.runtime` is the same instance, and `context.turns` now reads `RUNTIME`, so turns no longer need the agent server. `testPlugin` takes `servicePair(RUNTIME, runtime)`, given whole; `servicePair(AGENTS, { runtime })` keeps working.
- WebSocket routes: an `HttpRoute` may declare `websocket` (`WebSocketRoute`) to take WebSocket upgrades on its path, while every other request still reaches `handle`. An upgrade is a `GET` with `Upgrade: websocket`, a `Sec-WebSocket-Key`, and `Sec-WebSocket-Version: 13`; a `GET` missing the key or version gets `400` and other methods reach `handle`, all without calling `accept`. It then passes the route's `origins` allowlist (a missing or other Origin gets `403`; `"any"` skips the check; an entry that is not exactly a `scheme://host[:port]` origin, special such as `https://…` or non-special such as `chrome-extension://<id>` or `tauri://localhost`, is refused at startup, as is `"null"`) and `maxConnections` (256 by default; one more gets `503`), and then `accept(request)`, which authenticates before any socket opens and returns `{ data, headers? }` or a refusing `Response` (`WebSocketAccept`). Handlers get a `RouteSocket` (`data`, `send`, `close`); `send` answers a `WebSocketSendResult`: `"sent"`, `"queued"` behind a slow reader, or `"dropped"`. `maxBufferedBytes` (1 MiB by default) is checked before each `send`: once that many bytes wait for a client that stopped reading, `send` answers `"dropped"` and the socket is cut without a close frame, so the client and the route's `close` see 1006; nothing is dropped silently. A `send` that finds fewer waiting goes out whole, so one message larger than the limit still reaches a reading client and the bytes waiting can reach the limit plus one message; an empty message is `"sent"`. Every limit (`maxMessageBytes`, `maxBufferedBytes`, `maxConnections`, `rate.messages`, `rate.perMs`) must be a positive integer, or startup fails naming the route and field. Handlers may return any value, which is ignored; a promise is awaited. A message over `maxMessageBytes` (64 KiB by default) closes the socket with 1009, one over `rate` (120 a minute by default) with 1008, and a throwing handler closes only its socket with 1011 and logs the route and listener, never the URL. A throwing `accept` answers 500 with the fixed body. On shutdown every socket is closed with 1001 and the host waits up to five seconds for the routes' `close` handlers before stopping services. A route with `websocket` whose `methods` leave out `GET` is refused at startup. `pi-roundtable/kit`'s `serveUnix` takes an optional `websocket` handler and passes the server to `fetch`, which may answer nothing only when `websocket` is given. The guide's example spends each ticket once, and the guide warns against combining `origins: "any"` with cookie authentication.

- Kit: the class types of the built-in services (`AgentStore`, `AgentTeam`, `AvatarStudio`, `BackgroundTurns`, `ConfirmationJudge`, `Delegator`, `OwnerMemoryStore`, `PendingConfirmationStore`, `PiAgentRuntime`, `ScheduleStore`, `SkillRegistry`, `SkillStore`), replaced by the main entry's port interfaces where a plugin needs them, and the `*Options` types of those classes (`AgentTeamOptions`, `AvatarStudioOptions`, `BackgroundTurnsOptions`, `ConfirmationJudgeOptions`, `DelegatorOptions`, `PiAgentRuntimeOptions`, `SkillRegistryOptions`, `TeamTurnsOptions`), with `Detached`, `SkillEntry` and `SkillGroup`.
- **Renamed, for the unreleased types:** `OwnerMemoryStore`, `OwnerMemory`, `OwnerMemoryKind`, `OwnerPromptMemory` and `OWNER_MEMORY_KINDS` are `MemoryStore` (with `forSpeaker`, returning `SpeakerMemory`), `Memory`, `MemoryKind`, `PromptMemory` and `MEMORY_KINDS`; the tables and the tools' names do not change.
- Kit: `conversationKind()` and its closed `ConversationKind` (`"owner" | "party" | "agent"`); a conversation kind is any string that a claim's `startFresh` returns, and a plugin narrows the kinds of its own claims itself. `SessionContext.kind` is a `string`.
- Kit: `channelKey(channelId)` is `discordKey(channelId)`, because the main entry's `channelKey` builds a key on any surface.

- Addons: memory, skills, and Discord administration are built-in plugins of their own (`memory`, `skills`, `discord-admin`) that `defineRoundtable` adds unless the configuration switches them off with `memory: false`, `skills: false`, or `discord: { admin: false }`; all three are on by default. A switched-off addon contributes no tools, no prompt block, and no service, and its tables and rows are left untouched: `services.find(SKILLS)` and `find(MEMORY)` are `undefined`, the agents carry no skills, `agent_get` has no skills line, `agent_create` leaves out its `skills` parameter and refuses a call that passes some with an error saying skills are off, and `services.get` of an addon key fails naming the switch.
- `Contribution.toolTiers` (`Record<string, Tier>`): a plugin names the tier of each raw session tool it registers, as `defineTool` already does for its own; the operator's setting still wins and two plugins naming one tool are refused.
- `serviceKey(id, { absent })` and `ServiceKey.absent`: what a read of a service nobody provides says to fix it; `MEMORY` and `SKILLS` name their switches.
- `SkillRegistry.attach(agent, add, remove)`, which the agent team uses to give a new agent its skills.
- **Breaking (slash commands move under the Discord surface):** `Contribution.interactions`, `RoundtableOptions.commands`, `ChatSurface.useCommands` and the host's composition of commands are gone; the main entry no longer names `CommandRoot`, `ComposedInteractions`, `InteractionContribution`, `InteractionModule` or `RootOption` (they are in `pi-roundtable/discord`). A plugin that returns `interactions` from `setup`, a surface that has `useCommands`, and a host given `commands` are each refused with an error that names `context.services.get(DISCORD).commands.add(...)`, as `RoundtablePlugin.useCommands` is.
- **Breaking for the unreleased types:** the kit's Discord names moved to `pi-roundtable/discord` or were dropped: `DISCORD` and `DiscordServices` (now `connection`, `commands`, `guard`, `threads`; the owner's cards and the avatar studio are no longer published), `OwnerGuard` (now `CommandGuard`, a port), `ChannelExecutor`, `ChannelInfo`, `ChannelOperation`, `OwnerCommandHandlers`, `PanelContent`, `OwnerFacingError`, `groupOption`, `ownerCommandModule`, `ownerPanel`, `ownerPanels`, `ephemeralPanel`, `replyWithPanels` and `plain` moved; `DiscordSurface`, `DiscordSurfaceOptions`, `OwnerCards`, `OwnerCardsOptions`, `CardChannel`, `CardMessage` and `CardPayload` are gone (the owner's cards stay private to the Discord plugin and answer held actions through `context.surfaces.prompts`).
- `DiscordSurface.useCommands` is `setCommands` and is not published. `DiscordConnection` returns the public `AgentChannels`, `DashboardBoard`, `ThreadHost` and `OwnerOperations` (was `OwnerDiscord`) instead of the Discord classes, which removes five leaks from the type-leak baseline (now `ErrorReporter` only).
- `DISCORD_OWNER_TOOLS` is `DISCORD_ADMIN_TOOLS`.

### Changed

- **Breaking for the unreleased types:** `DefineOverrides` has five fields: `modelRuntime`, `logger`, `errorSink`, `listeners` and `aborted`. `errorReporter` is gone (set `config.ops` for the ops agent's reports, and `errorSink` for your own), `options` is gone (`options.listeners` is `listeners`, which adds listeners to the one `config.http` names, and `options.aborted` is `aborted`; the other host options come from the config), `modules.agentChannelOf` is gone (the modules read `AgentTeam.channelOf` from `AGENTS` when a tool runs), and `agentServer.ownerSessions` is gone (contribute `personas: [{ kind: "owner", prompt }]` and `requiredTools` from the plugin that owns the owner's conversations; the agent server no longer refuses a contributed `"owner"` persona). With no `"owner"` persona the owner's conversations start with an empty system prompt, as before.
- **Breaking for the unreleased types:** `AgentServerOptions`, `ModulesOptions`, `ErrorReporter`, `ErrorReportDelivery` and `ErrorReporterOptions` are no longer public: they were named by `DefineOverrides` only, and the public type-leak baseline is now empty. `Logger` is no longer pino's type, and `LogEntry` moved from `pi-roundtable/kit` to the main entry.
- **Breaking for the unreleased types:** migration names are unique inside a plugin, not across plugins (the ledger id is `<plugin>/<name>`), and `MigrationError.migration` and the start's error name that id. The same name in two plugins is allowed; a repeated id is still refused.
- The upgrade adds the ledger to a database that already ran the migrations without special handling: no id is recorded, so each `once` migration runs once more, as every start did before, and is recorded. **Rollback note:** a build from before the ledger ignores the table and runs every migration at every start; rolling forward again finds its ids recorded, so a `once` migration that fixes rows (for example one that gives rows written before speakers or guilds existed their owner or guild) does not run again over rows an older build wrote in between. Mark such a migration `runs: "every-boot"` if a rollback must converge.
- The host repository's tests use `migrateDatabase` where they migrated by hand, and its two import scripts read the ledger instead of migrating.
- **Breaking for the unreleased types:** the skills are provided by the new `skills` plugin, not by the agent server. the agent server takes no skills option (the paths are the `skills` config key's), the agent server provides only `AGENTS`, and the agent team reads the registry with `find(SKILLS)`, so the skill tools are the `skills` plugin's agent session tools (`skill-tools`) and its `agentSelection`, no longer part of `agent-tools`. `memoryPlugin` takes the `owner` and adds the `owner-memory` session tool, and `modulesPlugin` no longer adds that tool or `discord-admin`, which is the new plugin's.
- **Breaking for the unreleased types:** the core's tier table (`CORE_TOOL_TIERS`) names only `ask_user`, `compact_session` and `read_attachment`; the agent, schedule, delegation, web, skill and memory tools are declared by the plugin that adds them, with the same tiers. The Discord tools stay with the owner, as before.
- The order of the core's migrations is now memory, schedules, skills, held actions, agents, because the skills plugin sits before the agent server that reads its registry; all of them run before any setup and none touches another's tables. The stored data, the tool set, and each tool's tier under the default configuration are unchanged (a test records them for the owner's session, an agent's, and a group seat).
- The legacy skill kind `UPDATE` is no longer in the core's skill migrations; a host that still has skills stored under that kind converts them in a migration of its own, after the core's.
- **Breaking for a plugin that named it:** the built-in plugin list of `defineRoundtable` gains `discord-admin` (after `modules`) and `skills` (after it, before `agent-server`).

- **Breaking (the unreleased `InboundMessage` fields, and the second parameter's name of the published `ChannelClaim.owns`):** `InboundMessage` has neutral fields in place of Discord's. `guildId` is `space`, the server or workspace the channel belongs to; `webhookId` and `ownWebhook` are `integration?: { id, own }`, for a post by an integration such as a Discord webhook and whether it is the assistant's own voice; and `forwarded.channelMention` (`"<#id>"`) is `forwarded.source`, the forwarded-from channel's key. `ChannelClaim.owns(channel, guildId)` is `owns(channel, space)`; the parameter is positional, so callers do not change.
- **Breaking for the unreleased types (and the published `TurnEvent`):** `TurnEvent.agent` is optional and `TurnEvent` has `kind` (`"agent"` for an agent's turn, else the kind of a turn run through `context.turns`), so `turnStarted` and `turnEnded` also report those turns. `CoreAgents.runtime` is typed `AgentRuntime`, not the concrete `PiAgentRuntime` (the Pi runtime when no plugin fills the slot). `SessionContext.kind` is the turn's kind for a non-agent session, not always `"owner"`.
- `testPlugin`'s errors say what is possible inside it: `core service <name> is not provided yet` tells you to pass it in the `core` option instead of registering a built-in plugin, and a `conversations` call made from a handler no longer says it is "not during setup", since the harness links them.
- `DiscordSurface` implements `ChatSurface` (`surface = "discord"`, with `prompts`) and the Discord built-in contributes it: the `surface` service is now `surface:discord`, and a new `threads` service sweeps the dispatch threads once it has started.
- The agent server owns only `discord:` channel keys. A key of another surface, such as `mcp:<id>` on a host that claims those keys, whose id equals an agent's channel id was taken by the agent server at priority 100, because its ownership check sliced `discord:` off any key; it is now left to the claim that owns that surface.
  `AGENT_SERVER_PRIORITY` (100) is exported and documented: a claim on `discord:` keys with a lower priority is beaten in the agents' channels and in the rest of the agent guild.
- The stop button core posts is answered by the Discord built-in (owner only, through `conversations.stop`), so it works on a host that does not add its own handler.
- An unknown provider slot passed to `providers` is refused, naming the valid slots, as an unknown part of `setup` already was.
- Trim source tests and test-only helpers from npm contents; retain example tests embedded by the guide, excluding the guide verifier itself.
- Freeze shared protocol constants and publish readonly types; process-wide locale and time-zone setters are not exported by main, kit, or testing.
- Keep production integration inspectors out of testing and host-assembly values out of the kit.
- Without an `images` provider, agents get an avatar generated from their display name and the assistant's icon (a colour from the display name and the initial of the agent's name, always a Latin letter or digit, in a 512 px PNG served by content hash), instead of all sharing the neutral one. They are no longer offered drawing: `agent_create` has no `avatar_prompt`, `agent_avatar` is not registered, agents' prompts and `agent_get` leave avatar prompts out, and the profile panel says no image provider is configured instead of offering to redraw. Startup makes the missing pictures and logs one info line, not a warning per agent on every boot. A host with an `images` provider behaves as before.
- `roundtable doctor` has an `image provider` check, after `plugins`: it states whether a plugin fills the `images` slot and, without one, how to provide it; it is never a failure.
- `PluginContext.providers` also has `filled`, the set of slots a plugin fills, so a default can be told from a provider without calling it.
- **Breaking for the unreleased types:** the core no longer knows owner profiles. A held action carries an opaque `selectionId` (the `id` of the `TurnSelection` whose turn held it) in place of `PendingConfirmation.profile`; the core stores it and the caller resolves it when the owner confirms. `ConfirmationGate.beginTurn(selectionId, confirmed, addressee?)` takes that id, and a call held outside a turn throws instead of being stamped `"general"`.
- Held actions are stored in a new table, `held_actions(channel_key, selection_id, held_at, calls)`, which the core creates on every boot. A host upgraded from an earlier build keeps its old `pending_confirmations` table, which the core no longer reads; copy its rows across (`selection_id` takes the old `profile` value) in a migration of your own, after the core's.
- **Breaking for a plugin that named it:** the core extension `profile-tools` is named `active-tools` (a plugin may not take either name); `CoreExtensions.profileTools` is `activeTools`.
- Log and error wording: the stale-session reason `connectors changed` is `session tools changed`, the startup error `profile tools are not registered` is `required tools are not registered`, `profile tools missing; running without them` is `selected tools missing; running without them`, and the turn log's `profile` key is `selection`.
- **Breaking for the unreleased types:** the core no longer knows party channels. `BackgroundTurn.mode` (`"owner" | "party"`) is `BackgroundTurn.target`, a `string` naming a contributed `BackgroundTarget`; `Schedule.mode` and `NewSchedule.mode` are `target`, and `DelegationJob.mode` is `target`. The `schedules.mode` column keeps its name and its values (`"owner"`, `"party"`), which are now the target names, so no stored schedule is rewritten. The schedule tools' limits come from `ScheduleToolContext.target` (replacing `mode` and `SCHEDULE_LIMITS`), the delegator's running limit from `DelegatorOptions.targets(name)` (replacing the built-in table), and a target without `schedules` or `delegation` refuses both. The agent server's claim used to skip only `"party"` turns and now answers only `"owner"`, so a turn for any other target never reaches the owner's tools. The `/<root> schedule` list names a schedule's target by its label, or by its name when no plugin contributes it.
- The built-in plugin `stores` is split by feature, so one store can be replaced: `memory` (migrations and `MEMORY`) and `schedule-store` (migrations and `SCHEDULES`) come first, and the agent server now owns the tables it reads: held actions, and agents and groups; the skills have their own addon.
  The tables and the tools are unchanged.
- The default delegation worker is `WebResearchWorker` (it was named for one model), in `web-research-worker.ts`; it is not exported.
- **Breaking for the unreleased types:** `scheduleToolSpecs({ locale, timeZone })` takes the locale and the time zone its descriptions are written in, and `zonedStamp(date, timeZone)` (the kit's, a stamp in the zone you give) takes the zone, instead of both reading the process-wide setting. A worker of your own no longer sets the process's locale and time zone to get its tool descriptions in the wording and zone it wants. `useTestLocale({ locale, timeZone, assistant, root })` takes the same, with the neutral UTC and English defaults when called with nothing.
- The transitional local `pi-roundtable/internal` mapping is removed: the tsconfig path, `src/internal/`, and its guard test are gone, and a boundary test fails on any import of it and if the directory returns. It was never an npm export or part of the tarball, so a package consumer sees no change. `CardCadence`, `Expression`, `CardRenderError`, `packageDir`, `serveUnix` and the environment-variable parsers for tier members and tool tiers are no longer the core's: they moved into the host repository's own code, and the core does not export them.

### Fixed

- `defineRoundtable` no longer sets the process's locale, time zone, or `PI_CODING_AGENT_DIR`; `Roundtable.run()` applies the host's `environment`, so defining a second host no longer changes the first's.
- The root command `defineRoundtable` gives the host is built when `run()` applies the environment, so its description is in the host's language; `RoundtableOptions.commands.root` may be a `CommandRoot` or a function that returns one.
- One host runs per process: a second `run()` is refused with the fix. A failed `run()` stops what it started, closes the pool, and rethrows, and the same host may retry (tool tiers are declared idempotently per plugin).
- The shutdown drain waits on the host's own channel queue, not only on services, and the Discord built-in no longer contributes a `channel-queue` service.
- `shutdown()` runs once however many signals arrive and returns the exit code (non-zero when something did not stop or the boot had failed); only `listen()` exits the process, and the command line exits non-zero on a failed start.
- Importing `pi-roundtable/testing` in CI without a database URL no longer throws; repository CI requires its PostgreSQL URL in the workflow instead.
- Record the already-published main/testing API and CLI under 0.1.0 rather than presenting them as unreleased additions.
